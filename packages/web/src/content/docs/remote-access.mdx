---
title: Mobile Remote Access
description: Open your desktop workspace on a phone with QR pairing and approval.
---

OpenCtrlC Desktop can share its current local workspace with a phone through the OpenCtrlC Remote Relay. The desktop connects outbound, so you do not need to expose a port on your computer or start a web server manually.

## Connect a phone

1. Open the mobile access control from the phone icon in the desktop sidebar or title bar.
2. Choose **Enable mobile access** and scan the QR code with your phone.
3. Approve the phone in the desktop app. QR links can be forwarded, and the browser label is only a hint; approve only the device you are pairing. A QR link by itself does not grant workspace access.
4. Keep the desktop app running while you use the workspace on your phone.

The pairing link is valid only while its desktop session is active. Each browser needs approval once, then can reconnect while mobile access remains on. Browser approval expires after 30 days without use and is renewed as you use the workspace. The default limit is 10 approved browsers per session; you can set it to any whole number from 1 to 100 in the desktop access dialog. Lowering the limit does not revoke existing approvals, but no more browsers can be approved until the number is below the limit. In the desktop's approved browser list, you can revoke one browser while keeping the others connected; its browser label is only a hint and does not verify the physical device. Refreshing the QR code cancels pending approval requests. Choose **Stop mobile access** to revoke every approved browser. Closing or restarting the desktop app keeps the session and its approvals, so previously approved browsers reconnect without scanning again once mobile access is back on. If the desktop loses its relay connection unexpectedly, it retries the existing session, preserving browser approvals the whole time. Sessions with approved browsers stay recoverable for up to 30 days, matching the browser approval lifetime; empty sessions are cleaned up after an hour. A relay restart or an expired recovery window ends the session, so mobile access must be enabled again with a new QR code.

## Network and privacy

The desktop and phone use WSS/HTTPS to coordinate and to carry traffic when direct transport is unavailable. The relay forwards HTTP streams and WebSocket traffic to the desktop's loopback server. It does not open an inbound connection to your computer, and this deployment disables request access logs. Forwarded prompts, message bodies, and file contents are not intentionally persisted. When relay persistence is enabled, its recovery file stores session resume credentials, browser grants, and workspace metadata.

To restore the desktop's open workspace on a newly paired browser, the relay holds the open project paths, open session IDs, and active session ID in memory and, when persistence is enabled, in its restricted recovery file until the session is stopped or expires. It sends that index only to an approved browser. This index does not include prompts, drafts, or message bodies. These paths and IDs are sensitive metadata and are visible to the relay operator.

TLS protects each hop of the WSS/HTTPS path, but it is not end-to-end encryption: the relay decrypts traffic while forwarding it, so the relay operator could technically inspect content in transit. If a relay advertises the supported peer protocol and has ICE servers configured, the desktop and browser can carry traffic over a WebRTC DataChannel; that path uses DTLS and bypasses the relay for data. Signaling and ICE candidates still pass through the relay, and the peers may learn each other's network addresses. This does not protect against a malicious relay that alters signaling. If peer transport is unsupported or cannot connect, traffic stays on the WSS/HTTPS relay path. Review and trust the relay operator before enabling access. The desktop keeps its local server credentials on the desktop and does not send them to the phone.

The public relay at `openctrlc-remote.quniv.cn` is a single, limited-capacity deployment. Access speed and availability depend on its region and bandwidth. The relay source and deployment example are in [`packages/remote-relay`](https://github.com/ponponon/openctrlc/tree/dev/packages/remote-relay); teams can operate a relay in a region they trust.

## Choose a relay

New sessions resolve the relay target in this order:

1. The `OPENCTRLC_REMOTE_RELAY_URL` environment variable, when set (for development and testing).
2. The address saved under **Relay server** in the desktop's mobile access dialog.
3. The default relay `wss://openctrlc-remote.quniv.cn/v1/host`.

You can switch relays without rebuilding or editing source: open the mobile access dialog, paste a domain, an `https://` origin, or a full `wss://` address into **Relay server**, and save; the desktop completes the address for you. The new address applies the next time mobile access starts. An already-paired session keeps using the relay that holds its credentials until it is stopped, so existing phone approvals are not silently moved. A custom relay that cannot be reached fails with an error instead of falling back to the default relay. Choose **Use default** to return to the official relay.

## Can't reach the relay

Symptoms: mobile access stays on "Connecting…" or "Restoring…", the QR page does not open, or the desktop reports that it cannot connect to the relay.

1. Check basic connectivity first. The desktop needs outbound HTTPS/WSS; corporate proxies and captive portals are the usual cause. The default relay is a single, limited-capacity instance, and the desktop retries with backoff, so a short outage may recover on its own after a minute.
2. The official relay intentionally hides its health endpoint from the public web (public `/healthz` returns 404 by design), so a browser cannot confirm it is up. A QR page that opens on the phone only proves the phone's network path works; it does not mean the desktop side is connected.
3. If it keeps failing, switch relays: open the desktop mobile access dialog, paste an address you trust under **Relay server**, save, then stop and re-enable mobile access (see "Choose a relay" above). An unreachable custom relay shows an error instead of silently falling back to the default relay.
4. To run your own relay, see "Operate a relay" below.

Desktop-to-relay and phone-to-relay are independent paths: if the phone page loads but sessions do not work, the desktop side is the one that is offline.

## Operate a relay

See the [Remote Relay README](https://github.com/ponponon/openctrlc/tree/dev/packages/remote-relay) for its Docker Compose and OpenResty setup. A deployment needs a public HTTPS hostname, WebSocket upgrades, long-lived streaming timeouts, and a trusted TLS certificate. Restarting a single instance disconnects active transports and in-flight requests. If a persistent data directory is configured, the relay restores resumable sessions and browser grants so desktops can reconnect; in-flight streams are not restored.
